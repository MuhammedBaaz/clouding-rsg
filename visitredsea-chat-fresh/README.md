# Visit Red Sea site, fresh build: approved page + Empathy Studio web widget

A fresh copy of the approved Visit Red Sea home page (the V2/live markup, styles and assets) with **one** chat: the Empathy Studio web widget for the RSG web channel, embedded with the snippet the owner supplied. The old scripted chat (`js/chat.js`, Studio renderer port, data files other than `data/resorts.js`) is not loaded here. The previous builds (`../visitredsea-chat-mockup`, `-v2`, `-live`) are untouched.

## Run

```bat
start.cmd
```

Opens http://127.0.0.1:8100/ . `start.cmd` and `server.py` refuse to start when the port is busy and name the owning process; they never move to another port, because the Studio channel allows exact origins only. `python server.py 8130` runs on another port, which only works if that origin is on the channel's allowed list.

Configuration is `.env` (copy `.env.example`): `STUDIO_CHANNEL_KEY` (the channel's browser key, `acp_…`), `STUDIO_SSE_ENDPOINT`, `STUDIO_SDK_URL`, `STUDIO_AVATAR_URL`. The server turns them into `/studio-widget.js`, which is the supplied snippet verbatim:

```js
ChatWidget.init({ transport: { sseEndpoint: "https://acp-test.clouding.ai/api/v1/chat", apiKey: "acp_…" },
                  agent: { avatarUrl: "https://i.postimg.cc/TYg4S1HH/image-1794154482438.png" } })
```

The key is meant for the browser (the SDK sends it as `X-API-Key`); it is kept in `.env` only so it is not committed. No server credential (Anthropic key, SMTP) exists in this site. The Salesforce connected-app client id that was supplied alongside the snippet (`3MVG9…`) identifies a Salesforce OAuth client used by Studio's Agentforce agent type; this embed does not use it and it is not stored here.

## Widget appearance (10 November 2026)

The Web SDK reads its appearance only from the `ChatWidget.init({...})` config. It downloads nothing at runtime: core.min.js 1.14.0 makes exactly one kind of request, the chat endpoint, and the `ack` it receives carries only the visitor and session ids. Studio's **Customize** page therefore hands the whole configuration over as its **Copy snippet** output ("When the look is right, click Copy snippet and paste it into your site's HTML", Studio's own Web SDK Customizer guide). Only **Stream replies** is stored on the channel and read by the server.

So: `/studio-widget.js` now serves the config object from the file `private/studio-widget.snippet.html` when it exists (paste the Copy-snippet output there unchanged; the folder is never served and is gitignored; the file is re-read on every request, no restart needed), and falls back to the minimal transport + avatar config, which gives the SDK's default look ("Assistant", BETA badge, default colours). The startup line "Widget appearance: …" says which one is in use. Changing the look in Studio means: **Customize → Save → Copy snippet → overwrite the file → hard refresh the page (Ctrl+F5)**.

## Arabic RTL inside the widget, and «تحميل PDF» in one click (12 November 2026)

- **RTL (`js/widget-rtl.js`).** Read in the widget's open shadow root (core.min.js 1.15.0), the SDK renders text bubbles with `dir="auto"`, so a reply starting with "Shebara", a number or a link turns LTR. Lists keep a physical `padding-left`, so RTL bullets hang outside the bubble, and the same applies to `.cc-description` lists. Confirmation cards, carousel cards and pickers carry no `dir`, which leaves Arabic left-aligned and puts lines such as «SAR 28,980.00 · ليلتان» in LTR order. The page leaves the SDK as it is. It adds one style element (logical list padding) and sets `dir="rtl"` on every bubble, card and auto-direction text that contains Arabic. It also wraps dates («الجمعة 23 أكتوبر 2026», «23 - 25 أكتوبر 2026»), amounts («SAR 33,793.90») and phone numbers in no-wrap spans, isolating amounts and phones as LTR so a phone does not read «551234567 966+», and isolates Latin-only links. A MutationObserver re-applies all this after each re-render, because the text reveal rewrites a bubble's `innerHTML` on every tick. English-only bubbles keep `dir="auto"`. The carousel track stays LTR, because the SDK's arrows scroll by positive offsets.
- **PDF (`js/site.js`).** A Confirmation Card button only posts its payload (`t(primary_button_payload ?? primary_button_label, 0)`), and the SDK has no URL action. A capture-phase click listener reads the clicked card's payload from `widget.messages.get()`. When that payload is a same-origin `/trip.html?b=…&t=…` link, it opens the link and stops the click, so there is no visitor bubble, no agent turn and no second link. Every other button is left to the SDK. Studio template 14 has to put the bridge's `pdf` line in `primary_button_payload` (paste text in `../empathy-studio-preview/STUDIO_TEMPLATES_LIVE.md`, "12 November 2026"); until it does, the button keeps the two-step link reply.
- Verified on spare ports (site 8145 against a test backend on 8146) with cards injected the way the updated templates fill them (villa carousel, review, payment text, trip summary, a mixed bubble starting with "Shebara"). Desktop and 375 px both read right to left with bullets inside the bubble and no element overflowing. Measured order in the villa line and the ordered list: 23, then 25, then the month, then the year, right to left. Clicking «تحميل PDF» on the card opened `trip.html` for a recorded booking and the download started. In the same page with `window.open` recorded, the click opened the signed link, the message count stayed at 11 and no visitor message was added. The review button still went through the SDK. The Studio channel refuses spare origins (CORS), so nothing reached Studio during these tests.

## What the page does besides hosting the widget (`js/site.js`)

- Builds the resort cards (`data/resorts.js`, with each resort's official page on "Explore") and the assistant-added «اختر» buttons; «اختر» sends the approved customer line «نختار <Resort>.» into the widget's conversation the same way a card button does (SDK: `messages.add` + `transport.send`).
- «اختر» fix (9 Nov, live run): `transport.send` in core.min.js 1.14.0 takes the payload **string** (the SDK's own buttons call `messagesAPI.add({content, sender:"visitor"})` then `transportManager.send(content)`, and `send(t)` calls `t.trim()`); the page had passed an object, so the click added the bubble and threw before sending. Now it sends the string, and a refusal is logged instead of silently lost.
- Demo completion (10 Nov): the page watches for the payment-link message (lead-in «رابط الدفع الآمن» + visitredsea.com) and, 5 s after it appeared, sends the silent control line `rsg:continue` through the SDK transport once per message (sessionStorage guard across reloads). The bridge completes the demo booking once and replies with the trip summary and the demo loyalty points. No bubble is added for the control line; it does appear in Studio's session log.
- Trip PDF (10 Nov): `trip.html?b=<booking id>&t=<token>` fetches the completed booking through `/api/trip` (proxied to `RSG_BACKEND_URL`, default `http://127.0.0.1:8110`) and builds the PDF in the browser with `js/pdf.js` + `data/booking.js` (copies of the live build's generator and priced data). The chat's «تحميل PDF» button opens it directly when its payload is the signed link (12 Nov, below). Read-only: downloading again changes nothing.
- Page hand-off: `RSGPage.revealResorts(target)` scrolls to the cards, shows the «بانتظار اختيارك للمنتجع» bar and runs the V1 spotlight (`js/spotlight.js`); `endChoose()` cleans up. Because the SDK has no incoming-message callback, the page polls `messages.get()` and runs the hand-off when an agent message carries the approved sentence «خلني أوريك المنتجعات على الصفحة…».

## Verified facts about the SDK (read from `core.min.js`, transport "v2")

- Transport: `POST <sseEndpoint>` with headers `X-API-Key`, `X-Visitor-ID`, `X-Session-ID`; body `{"data":{"type":"text","text":…},"timestamp":…}` (first call `{"data":{"type":"init"}}`); the response is a stream of events `ack` (visitor_id, session_id), `status`, `streaming` (tokens), `message` (text, `rich_components` with `components`, or audio attachments), `stream_end`, `error`.
- A rich-component button posts its payload as a visitor message in the same session, then the agent answers.
- Public API from `ChatWidget.init`: `open/close/toggle/update/destroy`, `messages.get/add/set/clear`, `input.setValue/focus`, `session.sessionId/reset`, `transport.send`, `registerComponent`. Config keys: `transport`, `agent {name, subtitle, avatarUrl, betaBadge}`, `theme`, `position`, `dimensions`, `callbacks {onReady, onOpen, onClose, onDestroy, onMessageRetry, onScrollStateChange, onNewMessageIndicatorClick, onSend, onNewChat}`, `introduction {greeting, subtitle, quickActions}`, `welcome`, `launcher`, `input`, `features`, `typing`, `streaming`.
